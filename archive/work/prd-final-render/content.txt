Worklive Product Requirements
Product strategy and implementation plan
Version 1.0  •  30 September 2026  •  Proposed product direction
Recommendation. Build Worklive as a personal AI team that turns a clear brief into a finished, 
reviewable result. Its 3D office should help the user understand who owns the work, what is 
happening, and where intervention is needed. The first productive release should complete research 
and document tasks through the browser already present in the prototype.
This PRD defines the productive core, the relationship between real work and office life, the 
requirements for a trustworthy browser, and a staged route from the existing prototype. It also 
identifies useful concepts from TerminalOS and Workspace OS and compares closely related 
products.
Initial audience assumption. Start with an individual founder, creator, researcher or project lead who 
wants help investigating a topic and preparing useful work. Validate this audience before expanding 
into a software development platform or a general business automation suite.
First success. A user asks for a sourced comparison, watches an agent investigate the sources, 
receives an editable brief and comparison table, and can request a revision without restating the 
project. A second agent helps only when its distinct assignment improves the result.
Main product hypothesis. Persistent characters and visible work can make delegation easier to 
understand and more pleasant to return to. The hypothesis succeeds only if users finish valuable work 
with less supervision; visual appeal alone does not establish productivity.

2 The work Worklive should do
The recurring problem
Delegating work today often creates another conversation to manage. The user has to supply context 
repeatedly, discover what the agent actually did, recover intermediate files and decide whether a 
confident answer is usable. Worklive should keep the project, evidence, decisions and deliverables 
together across multiple runs.
The office provides a spatial overview of a small team. A project provides the durable context. Tasks 
describe bounded work. Artifacts are the reusable results. Conversation supports those objects and 
does not replace them.

Research is a practical starting point because evidence can be collected in the browser and assessed 
independently of the agent’s narrative. Document preparation builds directly on that evidence. 
Repetitive authenticated transactions have more dependencies and should follow after interruption, 
review and recovery work reliably.
Scope boundaries
The MVP includes one workspace at a time, projects, up to six visible agents, a maximum of two 
simultaneous model runs, and one live browser tab per running agent. It supports supplied public 
URLs and browser-based search, selected local text or Markdown inputs, plain-text and Markdown 
drafts, CSV comparisons, and a basic DOCX export. Model access starts with one supported provider 
behind an adapter.
The first release excludes arbitrary terminal execution, automatic external sending or publishing, 
purchases, broad account access, autonomous hiring, full Office editing, a room editor, multiplayer,

productive routines are the next stage. Existing cosmetic routines stay available.
The product should remain useful with a single agent. Adding desks must never be a prerequisite for

What the evidence changes
Positioning. Worklive should be a calm, persistent workspace for delegating knowledge work to a 
recognizable team. The defensible product opportunity is the quality of its task lifecycle, evidence, 
continuity and user control. The visual office contributes orientation and attachment, but competitors 
already use similar metaphors.
Collaboration. Anthropic reports that parallel research benefits from separate contexts, while 
coordination and token usage can rise substantially. Its internal results are specific to its system and 
do not predict Worklive’s performance. Worklive should compare one agent against a bounded team 
on the same tasks before making collaboration the default. [S11]
Architecture. OpenAI distinguishes a manager that calls specialists from a handoff that transfers 
conversational ownership. Worklive should use the first pattern for its initial shared projects: one owner 
remains accountable for the result. Frameworks can supply an execution loop, but Worklive must own 
its product state and tool authority. [S12] [S13]
Validation. There is no evidence yet that the office reduces supervision time or that users will pay for 
it. Test those hypotheses directly, including a simple list view as a baseline. Do not use repository 
popularity or competitor marketing claims as market validation.
4 The first complete user journey
Example project
The user creates a project called Customer research tools and asks: “Compare three feedback tools 
for a five-person product team. Use these vendor links. Check exports, collaboration, integrations and 
published pricing. Produce a two-page brief and a comparison table. Flag anything you cannot verify.”
1. Worklive proposes a compact task card containing the goal, output formats, source scope and 
stopping limits. The user can edit it and start immediately. Missing optional preferences become 
visible assumptions; missing information essential to the answer produces one focused question.
2. Ada owns the task. Her monitor shows the actual page being inspected. The task panel shows 
completed steps, the current action and source references. It does not invent a completion 
percentage for open-ended research.
3. If useful and allowed, Ada gives Milo a separate assignment to check export limitations across the 
same vendors. He receives only the project material and permissions required for that assignment. 
The user can see the assignment and its contribution.
4. A source that requires login becomes a visible blocker. The agent can continue independent 
research, use an alternative permitted source or ask for help. It must not invent inaccessible facts.

Worklive  |  5
5. The user enlarges Ada’s monitor and takes control. Worklive acknowledges the handoff after the 
active action settles; queued automation is invalidated. On return, Ada inspects the changed page 
before continuing.
6. Ada creates the comparison and draft brief. Automated checks verify the files exist and open, 
required sections are present, and source references resolve to captured evidence. A review pass 
flags unsupported claims; it does not certify every conclusion as true.
7. The task enters Ready for review. The user sees the files, evidence, assumptions, changes and 
usage. “Revise the recommendation for offline exports” creates a new run against the same project 
and preserves the prior version.
8. The user accepts the result. The project retains the brief, task history and approved decisions. Ada 
becomes available, and a cosmetic coffee break may begin without another model call.
Product promise
The same task can be completed from the flat workspace view. Office movement never blocks 
execution, and the user never has to wait for an agent to physically reach a desk or meeting table 
before work can proceed.
5 Screens and interaction design
Office. Show the agents, their actual work status and a small global strip for Needs you, Working and 
Ready for review. Clicking a character opens its task panel; clicking its monitor opens its current work 
surface. Labels, icons and text accompany color. Camera movement, sound and office life can be 
reduced or disabled.
Task panel. Show the goal, owner, inputs, next action, blockers, outputs, budget and controls. Offer 
Pause, Resume, Stop and Revise without exposing runtime terminology. A task’s evidence and past 
runs stay discoverable after its owner changes.
Expanded workstation. Tabs contain Browser, Conversation, Outputs and Activity. Browser work 
displays its real session. While an agent writes a document or uses an API, its desk can display the 
real artifact preview or activity summary with a clear label; no fake browser activity should be used to 
imply work.
Project view. Keep the brief, files, tasks, decisions and sources together. A compact task list supports 
keyboard access, search and sorting. Project switching updates context deliberately and does not 
grant cross-project access.
Review inbox. Separate decisions that are blocking execution from finished results awaiting review. 
Each approval explains the action, target, exact content or change, and consequence. A revision 
invalidates approval for the prior version.
Add an agent. The plus button creates a desk and identity with a role template, editable name and 
optional personality. Show capabilities and model separately. Creating a character does not silently 
start a paid run, add credentials or enable external actions.
Office life and real collaboration
Coffee, stretching, plant care and playful chatter remain local animation. Mark chatter as ambient and 
keep it out of task evidence. Personality can influence tone and cosmetic preferences; it cannot 
override permissions or quality requirements. Avoid simulated exhaustion, moods or friendships that 
change actual capability without an explicit user setting.

A real handoff may briefly animate two agents meeting and show a clickable summary such as “Milo 
shared three export limitations with Ada.” The runtime event triggers the animation. The animation 
does not trigger execution or grant permission. A waiting agent keeps its blocker visible even if it takes

An explicit user-requested brainstorm is real work: it has a brief, participants, a budget and a saved

Task lifecycle
The normal path is Draft → Queued → Running → Ready for review → Completed. Running may 
move to Waiting for user, Waiting for dependency, Paused or Failed. The user can cancel unfinished 
work. A run that produces a partial result reports the missing work and cannot claim completion. 
“Accepted” is an artifact review decision; it does not erase run history.
Waiting for user includes a structured reason: missing input, approval, browser takeover or login. After 
the reason is resolved, Worklive rechecks the task’s inputs and authority before resuming. A failed 
dependency blocks dependent work and leaves unrelated tasks runnable. Cyclic task dependencies 
are rejected.
Pause requests stop new model and tool dispatch. A non-cancellable action may finish before the 
pause is acknowledged. Stop cancels queued work and prevents new dispatch; it cannot undo an 
already completed external action. The UI must distinguish Requested, Acknowledged and Outcome 
unknown.

Worklive  |  7
Independent kinds of state
Task state, agent availability, browser control ownership and avatar pose are separate. A desk can 
show “Needs your input” while the avatar stands nearby. An agent can own queued tasks while no 
model is running. Every status change must be traceable to a runtime or user event.
One agent runs one task at a time in the MVP. Several identities may use the same model; several 
runs may reuse one identity. The avatar is not the process, and deleting or archiving an identity must 
not destroy completed project evidence.
7 Execution and collaboration logic
The execution loop
Worklive validates a task, builds scoped context, reserves a run slot and persists the run before 
contacting the model. The model proposes a next step. A tool broker validates its arguments, 
permissions, ownership and remaining limits, then executes the tool and records the observed result. 
The next model step receives that result. The loop stops on completion criteria, a blocker, cancellation, 
a repeated failure or a budget limit.
Progress text must come from actual actions and explicit plan updates. Show concise explanations of 
decisions and evidence, not private model reasoning. Tool attempts, successful actions and verified 
outcomes are different event types.
Delegation contract
The owner can assign an existing available agent a bounded subtask. The contract includes the 
question, non-overlapping scope, input versions, allowed tools, output format, acceptance criteria, 
remaining budget and parent task. Delegation cannot increase permissions or spend limits. The owner 
synthesizes the final result and stays visible as the responsible agent. [S12]
For the MVP, allow at most one helper and one delegation level. No autonomous creation of 
permanent agents. A helper returns an artifact reference, findings, evidence, uncertainties and a 
completion state. The owner may ask for one focused revision; repeated unproductive exchanges 
return a blocker to the user.
Agents communicate through task-linked messages such as assignment, clarification, evidence 
shared, review requested and result delivered. Messages are stored once with unique IDs. 
Acknowledgments do not trigger reciprocal conversations. There is no automatic all-agent broadcast 
or endless group chat.
Shared work without collisions
Parallel agents write to separate draft areas. One writer owns a target artifact version at a time. 
Promotion into the project checks the base version; a user edit or another accepted result creates a 
conflict to resolve. Browser control likewise belongs to one actor at a time. For future coding work, 
isolated worktrees solve source collisions but do not provide an operating-system security sandbox.
Scheduling and limits
The proposed default is two model runs across the workspace and six visible identities. More agents 
queue fairly, with explicit user priority. Enforce a configurable step limit, elapsed execution limit and

token or spend allowance per task. Waiting for user input suspends active execution time while 
retaining the task’s history.
Warn before exhaustion and reserve enough allowance to summarize partial results. Reserve

When a CLI or provider does not expose cost, display “Cost unavailable” and enforce observable turn,

8 Browser requirements
One session that the user can inspect
The desk preview and enlarged browser must represent the same agent, run, browser session and 
tab. Frames carry a timestamp and navigation identity. A stale, disconnected or hidden frame is 
labeled accordingly. Changing agents cannot show a previous agent’s frame as current.
Use structured browser actions for navigation, observation, links, forms, scrolling, text extraction and 
screenshots. Prefer stable element references from the current page observation; use coordinate 
interaction when necessary. Bind actions to the observed navigation version so stale actions are 
rejected. Verify the postcondition of meaningful actions instead of equating a successful click with task 
success.
The MVP begins with public information and one tab per running agent. A transient browser context is 
distinct from an agent identity. Login persistence, popup-dependent authentication, multiple tabs and 
downloads need explicit subsequent support and tests. OpenClaw and Manus illustrate the product 
distinction between isolated contexts and existing authenticated sessions. [S7] [S8]
Take control and return control
Take control immediately prevents new automation from entering the queue. The current action settles 
or times out, ownership changes, and the UI acknowledges user control. A timeout with an uncertain 
action outcome remains visible. The user can navigate and interact with the same session. Model 
observations from before the takeover become stale.
Return control gives the agent a fresh observation and a short record that the user changed the 
browser. The agent revalidates its plan and any pending approval. Stop remains available in both 
modes. Neither takeover nor stop claims to reverse a submitted form.
Authority and exposure
Remote pages cannot invoke Tauri commands, read project files or access credentials through the 
renderer. Browser capabilities are routed through the broker, with run-scoped ownership and project 
policy. Block unsafe schemes, unauthorized local-network destinations and attempts to bypass scope 
through redirects. An explicit local development mode is separate from normal public browsing.
“Research only” is a permitted workflow scope, not a guarantee that arbitrary web clicks have no side 
effects. Browser actions can mutate server state even without a familiar submit button. Avoid 
authenticated transaction workflows in the MVP, use constrained navigation and extraction where 
possible, and require a specific reviewed action before supported consequential mutations in later 
releases.
In a later login mode, the user chooses a dedicated account profile and signs in directly. Profile reuse 
requires explicit project or workspace sharing rules. No silent personal-cookie import. Credential entry

9 Artifacts memory and review
Results that survive the conversation
A task that promises a file must produce a real, readable file. Save drafts atomically in a run-owned 
area, validate the format, then register the artifact with its hash and source references. The output 
view offers Open, Reveal in folder, Revise and Accept. A task must not claim that it saved a file based 
only on model text.
For a research brief, retain a source list with titles, URLs, retrieval dates and the evidence used. Each 
material factual claim should have supporting evidence or be marked as an inference or unknown. 
Capture failures and source disagreements remain visible. Citations prove where a claim came from, 
not that the claim is necessarily correct.
DOCX export should use a constrained document schema and a maintained renderer. Validation 
covers both the saved file and a rendered preview. CSV output checks headers, rows and encoding. 
Preserve prior accepted versions. Worklive needs basic readable output before it needs the full 
Workspace OS editing suite.
Review and reversible changes
Results arrive with a short statement of what was done, what changed, checks performed and 
remaining limitations. Review can accept the result, request a focused revision or discard the new 
draft. Applying an edit to an existing file checks its current hash and preserves a recoverable prior 
version. A conflict must not silently overwrite the user’s work.
Workspace OS provides useful checkpoint and diff concepts, but its whole-workspace rollback should 
not be copied directly into concurrent Worklive runs. Reverting one agent’s output must not roll back 
another agent’s accepted result or a user’s unrelated changes. Reversal also cannot undo email, 
purchases or other external side effects. [L2]
Three scopes of memory
Run memory holds the working conversation and intermediate observations. Project memory holds 
briefs, verified findings and accepted decisions. Agent preferences hold user-approved instructions 
such as tone or preferred format. Share information only through explicit project access and handoffs.
Store a source, scope, author, revision and timestamp with durable facts. Let the user inspect, correct, 
delete and exclude them. Contradictory new evidence creates a proposed update rather than silently 
rewriting an accepted decision. Summaries are derived material and must preserve links to the 
underlying sources. LangGraph’s separation of checkpoints and long-term stores is a useful 
implementation reference. [S15]
Start with explicit project notes and local full-text retrieval. Defer a vector database until retrieval 
evaluation demonstrates a need. Do not turn casual office chatter into durable factual memory.

10 Permissions privacy and failure recovery
Enforced capabilities
Role and personality describe behavior; capabilities grant authority. Enforce permissions in the tool 
broker outside the prompt. Grant selected input files, run output directories, browser scope and 
approved connectors independently. No arbitrary shell is exposed in the initial release. Deny-by-prefix 
shell rules are not an adequate sandbox for a later coding edition.
Automatic validation and human approval solve different problems. Worklive should validate every 
supported action and request approval when its consequence requires a decision. Reading permitted 
sources and creating drafts within the assigned output area should not prompt repeatedly. External 
sending, publishing, destructive changes and expanded access require an explicit supported approval 
flow. [S14]
Approval is bound to exact parameters and resource versions. Changed recipients, content, target 
state or scope invalidate it. Denial is recorded and cannot be bypassed through delegation or another 
tool. The request remains understandable after a restart. n8n’s tool review model is a useful reference 
for presenting the concrete action. [S10]
Untrusted material and secrets
Pages, files, connector results and agent messages are untrusted inputs. They cannot change system 
policy, grant themselves access, request secret export or install tools. Preserve their provenance and 
avoid converting embedded instructions into authority. Use scoped tools, explicit data boundaries and 
adversarial tests; no prompt alone makes browsing immune to manipulation.
Store provider credentials in the operating-system keychain and pass them only to the authorized 
adapter. Local storage does not mean local inference: show which selected content is sent to a model 
provider. Allow project deletion and evidence retention settings. Default to no full browser recording, 
no background transcript collection from unrelated apps, and no task content in telemetry. Diagnostic 
sharing must be explicit and redact secrets.
Recovery behavior
Persist action intent before execution and record the result afterward. A crash between those steps 
can leave the outcome unknown. On restart, reconcile observable state; retry safe reads, but do not 
blindly repeat an external mutation. Idempotency keys help only when the receiving service supports 
them. Never promise universal exactly-once external execution.
Checkpoint boundaries must avoid replaying side effects. LangGraph documents that interrupted 
nodes restart from their beginning when resumed, which makes replay-aware tool design necessary 
even when a framework persists state. [S16]
Worker crashes fail the affected session visibly, preserve accepted artifacts and release control only 
after reconciliation. Provider failures use bounded retries with backoff. Repeated failures become a 
blocker. Sleep or network loss suspends useful work; the UI explains what will resume. Closing or 
quitting behavior must be explicit, and a local-only release cannot promise work while the machine is 
off.

11 Recommended architecture
Keep the current foundation
Continue with Tauri for the native application and Rust for durable state, scheduling, process 
supervision and permission enforcement. Keep Three.js for the office and TypeScript for the interface. 
Use a separately supervised browser and model worker where the browser automation and model 
libraries are mature. A Rust-based desktop application can legitimately include those workers.
The browser service already separates remote pages from the Tauri UI. Extend that seam rather than 
embedding agent authority into scene objects. Persist state in SQLite with migrations and transactional 
task claims; keep artifacts as ordinary versioned files. The office subscribes to a projection of events 
and can be replaced by a flat interface without changing execution.

Tauri and Electron decision gate
Electron offers offscreen rendering, including GPU texture paths, which could help future screen

measurement. Tauri supports packaging external binaries, but shipping a browser and worker remains 
an application responsibility. Neither framework choice removes browser security or memory costs.

authentication limitations or distribution complexity that Electron materially resolves. Run the same six-
desk scene and two active browser tasks in any comparison. Evaluate whole-app memory, CPU, input 
latency, crash isolation and clean-machine installation, not framework download size alone.

outcomes are surfaced without blind replay. Completed artifacts remain readable.
FR07 P0 Produce reviewable artifacts. A brief, CSV and DOCX open successfully, retain sources 
and versions, and support a focused revision with the old version preserved.
FR08 P0 Enforce scope and approvals. Denied actions cannot execute through a helper or alternate 
supported tool. Changing approved parameters invalidates the decision.
FR09 P0 Bound collaboration. One helper can complete a distinct subtask with evidence; the owner 
produces the final result. Delegation depth and total limits cannot be exceeded.
FR10 P0 Protect concurrent edits. A changed base file raises a conflict. Accepting or discarding one 
draft preserves another agent’s outputs and unrelated user edits.
FR11 P0 Offer equivalent flat controls. Keyboard users can create, inspect, pause, take over, review 
and revise without interacting with the 3D scene.
FR12 P0 Respect idle and budget limits. Cosmetic routines generate zero model calls. When a limit 
is reached, no new action is dispatched and partial results are retained.
FR13 P1 Support dedicated persistent login profiles. Restart retains an explicitly selected profile; 
another project or agent receives no implicit access.
FR14 P1 Run productive routines. A missed schedule catches up at most once; overlapping 
instances never run. Disable prevents future dispatch and reports any active run.
FR15 P1 Add a second runtime or connector. It conforms to the same ownership, policy, 
cancellation, evidence and capability-reporting contract.

16 Adoption economics and open decisions
Pilot and positioning
Recruit five to eight people who already delegate research or drafting at least weekly. Include the 
creator’s own real projects. Ask each person to bring an actual comparison or brief and run three work 
sessions over two weeks. Observe what they correct, where they take control and whether they return 
without prompting.
The primary pilot measure is accepted useful artifacts per active user week, paired with active 
supervision time. Also track task completion, revisions, failure reasons and repeat use. As an initial 
directional target, seek at least three completed useful tasks per returning user per week and lower 
supervision time than their previous process. Keep the pilot small enough to investigate every failure.
An initial product hypothesis is a desktop subscription with transparent bring-your-own-model costs. 
Managed execution could be a separate future offering. Do not price by the number of visible desks: a 
character is not a reliable proxy for compute cost. Do not promise unlimited autonomous work. Test 
willingness to pay after repeat utility and support costs are visible.

 Audience. Is the first paying user a general knowledge worker, a software creator or an operations 
lead? This PRD recommends the first and preserves a path to the others.

choosing the first adapter.
 First output format. Validate whether a brief plus CSV and basic DOCX is enough, or whether 
real pilot work requires deeper Office editing immediately.
