WORKLIVE — SCREEN LANDSCAPE
Screen plan and source review · 1 October 2026

DIRECTION
The user selected the Screen Landscape image: an open, quiet space containing
thin agent screens, with one pulled forward for focused work. The interface
should preserve this visual identity while making everyday actions direct.
This is a design study, not an implemented replacement for the office.

The product has one environment with several views, rather than ten unrelated
applications. Overview shows identities and status; focus gives a screen a
readable, face-on working size; temporary sheets handle menu, context and review.
Depth establishes which object is selected. It should not make reading harder.

WHAT I INSPECTED
The current working source and README: src/main.ts, types.ts, projects.ts,
context.ts, task-files.ts, documents.ts, inbox.ts, workflow.ts, office/hire.js,
and worker task admission in agent-runtime.mjs. These are source capabilities;
this session did not run CLI tasks or verify the packaged app. The shared log
still reserves application editing to Claude, so all work here is separate.

The existing app already provides:
- Named agents, roles, personalities, provider choice and character appearance.
- Official Codex / Claude Code connection checks and terminal sign-in.
- Bounded tasks with manual start, pause, stop, resume and revision.
- Browser previews and explicit user takeover. Taking control pauses the task;
  returning control does not automatically resume it.
- Local per-agent chat history. Chat sends use official provider CLIs, carry
  profile/status/task brief and recent messages, and do not use tools.
- Projects, goals, team membership, planned tasks and one prerequisite per task.
- Personal, project and company memory; local reference-file imports; versions,
  pins, archive/restore, company-memory proposals and provenance.
- Task-specific references, formatted document reading/editing, and file search.
- Questions, blocked work, result review/acceptance, and reviewed single-file
  handoffs that create planned tasks.

The new spatial layout, focus transitions, overview filtering and "Prepare
task" shortcut from chat are proposed presentation/workflow changes. They are
not current capabilities merely because a generated picture shows them.

PRIMARY JOURNEYS
1. First use:
   Connections -> sign in through an official tool -> recheck -> Create agent
   -> Team overview. The agent is idle until the user starts a task.
2. Real work:
   Overview -> select agent -> Task -> write a brief and choose project/task
   context -> Start -> Browser/Results. Chat is not a hidden task-launch button.
3. Conversation:
   Select agent -> Chat -> discuss. "Prepare task" would copy a reviewed brief
   into a task composer; it would not execute or silently grant file access.
4. Missing information:
   Agent question -> Inbox or its attention tab -> answer -> explicitly send
   answer and continue. This is a run continuation, separate from casual chat.
5. Finished work:
   Inbox -> read result and sources -> revise or Mark accepted -> optionally
   hand off one file -> review exact content and recipient -> authorize and
   queue -> start the new task separately.
6. Context:
   Agent Context or global Library -> choose scope -> read/import/edit ->
   return to task. Task-only files stay distinct from reusable library files.

SUPPORTING SHEETS AND STATES
These belong to the core views above, not additional permanent navigation areas:
- Task composer: title, brief/expected deliverable, owner, prerequisite, project;
  task files become attachable after the planned task is saved.
- Agent profile: edit name, role, personality and optional existing appearance;
  preserve all current character data even if the landscape does not display it.
- File finder (existing Command-P / Command-K): results, notes, library files,
  task references; open the shared reader/editor.
- Document reader: formatted/source view, version-aware edit/save when allowed,
  extracted text for PDF/DOCX, and read-only explanation when edits are locked.
- Task detail/history: earlier runs, current run, source evidence, context
  supplied, memory additions, event log, revision and provider interruption.
- Company proposal review: publish the specific reviewed contribution.
- Project settings: brief and definition of done, membership, one working
  project per agent; changes affect subsequent context.
- Connection failure/recovery: missing CLI, sign-in needed, unavailable worker,
  subscription limit, interrupted task; clear check/reconnect/resume action.
- Empty states: no agents, no project, no tasks, no memory, nothing in inbox.
- Browser states: opening, live, last capture with timestamp, user in control,
  failure and retry. Never show an old screenshot as if it were live.

PRODUCT RULES TO PRESERVE
The screenshot is presentation; existing authority checks stay in Rust/worker.
Codex identity stays teal #2D9D8F; Claude Code stays terracotta #D97757, accompanied
by a provider label. Any character shirts keep these colors. Attention and
acceptance use separate labels/icons; global memory scopes have no provider.

The runtime currently allows two active task runs total, one per provider.
A twelve-person overview does not mean twelve working CLI sessions. Chat has
its own existing path; the two-task limit is not a claim about all subprocesses.

Personal/project/company scopes remain distinct and provider-independent.
A task file is not automatically a project file. The current chat implementation
does not retrieve the full memory/file library; do not imply file-grounded chat
without explicitly implementing a scoped retrieval path.

Review is not acceptance, acceptance is not sharing, and queuing is not starting.
A prerequisite unlocks order after acceptance; it does not transfer a file.
A handoff preserves one reviewed file snapshot and the next-step brief; it does
not copy source notebooks or conversations. Source checks must remain intact.

Read-only context and result inspection may remain available during work.
The current app locks shared-plan/context/review changes while tasks run.
The design must show why an action is unavailable, and let the user pause work
deliberately. Opening a review view must not silently pause running agents.

Do not move files/memory between scopes with an unconfirmed visual gesture.
An optional drag shortcut may open a scoped task/attachment/handoff sheet; the
existing checks and explicit user actions remain authoritative.

INTERACTION AND ACCESSIBILITY
- One click or Enter brings a screen forward; Escape returns one level.
- Use the same agent identity across Browser, Chat, Task, Context and Results.
- The global capsule is consistent: Overview, Inbox, Projects, Library, Menu.
- Global project selection is a VIEW FILTER, not a project reassignment.
- Keep focused content face-on and opaque enough to read. Distant screens
  orient the user but do not force interaction with tiny perspective text.
- Provide keyboard focus, shortcuts, screen-reader names, legible contrast,
  reduced-motion transitions and click alternatives to every drag gesture.
- Do not continuously orbit, bob or zoom screens. Move only on interaction.
- At larger roster sizes use compact bands/filtering and bounded previews.
  The twelve-agent image is an example, not a proven capacity limit.

LIGHTWEIGHT IMPLEMENTATION CANDIDATE
Prototype the shell with ordinary accessible DOM controls and shallow CSS
transforms over a static background; live browser images can use the existing
capture stream. A full 3D engine is not required merely to depict angled planes.
Avoid making every empty sheet a permanent Chromium instance. Idle sheets can
show honest standby/result states; browser lifetime and capture throttling need
a deliberate implementation, not just a visual redesign.

Measure the actual Tauri build with representative tasks, viewport, capture
rates, CPU/memory pressure and frame-time stalls. These still images do not
establish smoothness, energy usage or latency.

SUGGESTED FIRST PROTOTYPE
Build a separate thin shell with Overview -> Focused browser -> Chat -> Menu,
using sample or read-only state first. Validate one-click access, legibility,
keyboard navigation and a return-to-overview gesture. Then connect the existing
task lifecycle, Inbox, Library and Projects. Keep the office available during
evaluation; this exploration alone does not authorize deleting it.
A useful product check is whether a user can locate a blocked agent, inspect its
evidence, supply an answer, and return to the team without getting lost.
